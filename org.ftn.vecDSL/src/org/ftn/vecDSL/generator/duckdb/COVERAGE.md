# vecDSL coverage: DuckDB

DuckDB 2.0.0 (MIT, released 2026-10-21) with the core extensions vss (HNSW indexes, experimental) and fts (BM25), embedded: no server, one database file per program (`VECDSL_DUCKDB_PATH`, default `vecdsl.duckdb` in the program's folder). Python `duckdb` 2.0.0 to <2.1 with `duckdb-core-ext-vss` and `duckdb-core-ext-fts` 2.0.0, TypeScript `@duckdb/node-api` 2.0.0-r.1 (the Neo client), Java `org.duckdb:duckdb_jdbc` 2.0.0.1 with Gson 2.13.2 (versions checked on 2026-11-14). Rows are generated from `model/generated/VecDSL.ecore`: every concrete Method, Concept, AlterOperation and ExtensionItem class, then every structural feature of each Method class. Status: native (one SQL statement or catalog query DuckDB offers for the construct), concealed (SQL that composes DuckDB features into the exact vecDSL semantics), unsupported (DuckDB and its core extensions lack it; the generator raises the message), not-applicable (cannot occur for an embedded DuckDB target; the generator raises the message where the grammar allows the construct). Rows whose notes start with \"generation pending\" are native or concealed in DuckDB but not generated yet; they raise \"... has no DuckDB mapping yet\". The SQL text is built by the generator (`DuckdbSql.java`, `DuckdbQueries.java`) and executed by `vecdsl_duckdb_runtime.py`, `vecdslDuckdbRuntime.ts` or `DuckdbRuntime.java`, so the Python, TypeScript and Java programs send identical statements and bind values. References point to the DuckDB 2.0 documentation and to the vss sources at the commit of the 2.0.0 extension build (3685131eac).
